Database design & experimentation

The core problem was turning a raw NFC uid into a meaningful attendance record. Three storage approaches were evaluated against the constraints of a single Raspberry Pi prototype: no server to administer, the ability to query with SQL, and reliable timestamped writes.

Final schema · backend/database.py
CREATE TABLE students (
  id    TEXT    PRIMARY KEY,
  name  TEXT    NOT NULL,
  year  INTEGER,
  class TEXT,
  uid   TEXT    UNIQUE
);

CREATE TABLE attendance (
  id         INTEGER  PRIMARY KEY AUTOINCREMENT,
  student_id TEXT,
  timestamp  DATETIME DEFAULT CURRENT_TIMESTAMP,
  date       TEXT,
  FOREIGN KEY (student_id) REFERENCES students(id)
);
Options evaluated
Flat file · CSV / JSON Rejected
No relational lookups or concurrent-safe writes — every query would mean re-parsing the whole file by hand.
MySQL / PostgreSQL Deferred
Production-grade concurrency, but needs a running server and configuration — heavier than a single-device proof of concept requires.
SQLite Chosen
Serverless and file-based, ships with Python (import sqlite3), and supports SQL queries with foreign keys.

Why SQLite was selected: SQLite was appropriate for the prototype because it runs locally on the Raspberry Pi, requires no external server and is simple enough for a single-device proof of concept.
Ongoing Evaluation

The SQLite database gave Vero a reliable structure for converting raw NFC scans into meaningful attendance records. This was necessary because the website needed more than a UID; it required a name, class, timestamp and attendance status. However, SQLite may be limited for a full school deployment because a larger system would require stronger concurrency, authentication and cloud backup.
